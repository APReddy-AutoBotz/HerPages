# Bolt acceleration playbook

## Purpose

Use temporary build capacity to produce portable, tested product work. Do not let a builder's convenience reshape the privacy architecture. The offer duration is verified in the owner's account; no specific end date is assumed. GitHub integration is documented by Bolt, but current branch/sync behavior must be tested for this repo. [S08]

## Master build instruction

```text
You are implementing HerPages in the existing GitHub repository. Read AGENTS.md, STATUS.md, PRD.md, ARCHITECTURE.md, TECH_STACK.md, the relevant trust documents and the assigned backlog task. Preserve HerPages and its tagline. Work only on the assigned coherent tranche. Use synthetic data. Do not deploy, provision paid services, enroll real minors or connect production accounts.

Start by reporting the exact branch/commit, task IDs, existing files, toolchain compatibility and implementation plan. Keep native vault storage separate from service/cloud data. Never use browser localStorage or a plain SQLite fallback for sensitive content. A browser preview is only a demo, not native encryption proof. Do not invent police, AI, payment, assurance or partner integrations.

Implement contracts and tests together. Record limitations, update STATUS.md and handover notes, and stop at the task's release gate. Never call a skipped test passed. Do not start community, live location or private cloud AI unless their explicit gates have passed.
```

## Tranches

**A — Portable foundation:** HP-002, tokens, route shells, schemas, synthetic fixtures and validators. Native compatibility spike starts immediately, not after building 40 web screens.

**B — Useful private slice:** HP-003/005/006/010. Create/lock/save/search an encrypted Page, import encrypted media, export/restore and show accurate storage status. If the environment cannot build native modules, implement only interfaces/UI/tests and clearly hand off the native work; do not fake it.

**C — Connected but bounded:** catalog/editorial UI, policy API contracts, organization drafts, offline directory and synthetic consent flows. Production account/child/recovery integrations remain gated.

**D — Hardening/handover:** clean branch, dependency lock, schema review, test results, setup instructions, known gaps and a clean-room Codex run. Remove abandoned generated variants and secrets. Preserve deliberate architecture decisions.

## Daily control

One integration branch owner. Sync GitHub before/after changes; inspect actual diff. Keep PRs reviewable. Do not overwrite migrations/contracts with parallel builder prompts. Check current vendor data-use terms; never upload private diaries, real child records, employer/client documents or identity proofs to builder chats.

## What not to spend capacity on

Ten disconnected dashboards; fake live integrations; visual-only 'security'; a new brand; complete adult social networking before moderation; a universal law checker; native encryption rewritten as a web storage demo. More generated code is not inherently more progress.
